# Twitch Browser Extension Exposes 30,000 Users’ OAuth Tokens to Russian Bot Service

A Twitch browser extension on Chrome and Firefox forwards users’ live OAuth session tokens through proxies controlled by a Russian bot service.

* Kush Pandya

|6 min read

*Update, September 25, 2026: The fix is live on the Chrome Web Store. We confirmed that Chrome Web Store version 85.8.9 (the current version at this time) no longer forwards the viewer's Twitch OAuth token to the proxy. We've also revised the IOC section and removed the recommendation to block all listed infrastructure.*

*Update, September 16, 2026: After publication, the JeetBot team reached out to us. They acknowledged the security risk of the token handling and that the extension's store description and privacy policy did not adequately disclose it, and they released a fix. We confirmed the remediation in the code: Firefox version 85.8.7 no longer forwards the viewer's Twitch OAuth token to the proxy (the auth parameter is now hardcoded to empty and auth-token parameters are stripped). The same fix has been submitted to the Chrome Web Store and is awaiting review; the current Chrome build (85.8.4) still forwards the token, and any installation running the older code continues to forward until it updates.*  
Socket’s Threat Research Team identified a cross-store browser extension, “Twitch Enhanced Viewer | JeetBot,” that forwards each user's live Twitch OAuth session token to third-party proxy servers operated by the JeetBot service. The extension ships on both the Chrome Web Store (extension ID [`pnhhdhhcadcjfckjhpmjneldiegbojfb`](https://socket.dev/chrome/package/pnhhdhhcadcjfckjhpmjneldiegbojfb), 30,000 users) and Firefox Add-ons ([`twitchenhancedviewer@example.com`](https://socket.dev/firefox/package/twitchenhancedviewer@example.com), 552 users). Both listings are live at time of writing.

* Current builds (v85.x) forward the token inline as an `&auth=` query parameter on a network-layer redirect to the operator's proxy. The token is forwarded for every channel the user watches, except a hardcoded allowlist of ten Russian streamer channels, whose sessions are exempted from forwarding.
* Earlier v4.x builds (for example version 4.8, January 2026) went further, POSTing the token to a dedicated set-token endpoint on the operator host, with backups on deno.dev and [deno.net](http://deno.net).
* The operator is a commercial Twitch, Kick, and VK-Live bot SaaS that has broad Twitch host permissions and relays live authenticated sessions through its own infrastructure.

*The JeetBot extension's attack lifecycle, from marketplace listing to the live Twitch OAuth token reaching operator proxies.*

## What the Extension Claims to Do[#](#What-the-Extension-Claims-to-Do)

“Twitch Enhanced Viewer | JeetBot” markets itself as a Twitch quality-of-life tool: block Twitch ads, force 1080p and region-unlock streams, and auto-collect channel points. That value proposition is real and is why users install it, and the extension also forwards the user's Twitch OAuth token on that same request. To deliver ad-free and region-unlocked video, the extension redirects Twitch’s video-playlist requests through operator-controlled proxy servers. The user’s Twitch OAuth token rides along on that redirect.

*The Chrome Web Store listing for Twitch Enhanced Viewer, showing 30,000 users and the `jeetbot[.]cc` developer link.*

*The Firefox Add-ons listing for the same extension, reporting 552 users.*

## How the Token Is Captured and Forwarded[#](#How-the-Token-Is-Captured-and-Forwarded)

### Capturing the token from the Twitch page[#](#Capturing-the-token-from-the-Twitch-page)

The content script reads the `Authorization` header that Twitch’s own web client uses and relays it to the extension background worker. In [`src/scripts/content.js`](https://socket.dev/chrome/package/pnhhdhhcadcjfckjhpmjneldiegbojfb/files/85.5.1/src/scripts/content.js), the captured header and Twitch device id are passed over the extension’s internal bridge:

JavaScript

```
 return _sendBridgeMessage("tev-proxy-session", { authorizationHeader: __TEV_STATE__.AuthorizationHeader || null, deviceId: __TEV_STATE__.GQLDeviceID || null, }); return _sendBridgeMessage"tev-proxy-session" authorizationHeader AuthorizationHeader null deviceId GQLDeviceID null
```

The background worker stores that value and later strips the prefix to recover the raw token. That the value is the Twitch OAuth token, not an extension-specific device token, is confirmed by how it is used: the same token is sent as `Authorization: OAuth ${token}` to Twitch’s own token-validation endpoint in [`src/scripts/background.js`](https://socket.dev/chrome/package/pnhhdhhcadcjfckjhpmjneldiegbojfb/files/85.5.1/src/scripts/background.js#L515):

JavaScript

```
 const response = await fetch(TWITCH_TOKEN_VALIDATE_URL, { cache: "no-store", headers: { Authorization: `OAuth ${token}` }, }); const await fetch TWITCH_TOKEN_VALIDATE_URL cache"no-store" headers Authorization`OAuth ${token}`${token}
```

This is the account-scoped Twitch OAuth token, which grants access to chat, whispers, and account settings, not the narrow stream-playback token. The extension already handles the stream token separately (it is present in the usher URL as token and sig), and its own token-strip path routes some channels through the proxy with no token at all, so appending the full account credential exposes far more than fetching the video requires.
