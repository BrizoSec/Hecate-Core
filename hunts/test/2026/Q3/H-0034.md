## OBSERVE: Expected Normal

### Hypothesized Normal Range

Office apps (winword.exe/excel.exe/outlook.exe) spawning helper processes like splwow64.exe at high frequency across most hosts; explorer.exe spawning common user apps (chrome.exe, cmd.exe, notepad.exe).

### What Would Be Anomalous

Office applications spawning script interpreters or LOLBins (powershell.exe, certutil.exe, mshta.exe, cscript.exe) -- especially at very low event/host counts, since that pattern doesn't match normal document-editing behavior.

Based on the (synthetic) frequency table: explorer.exe → chrome.exe and explorer.exe → outlook.exe dominate (48,211 and 41,022 events, on 487 and 465 of ~500 hosts). winword.exe/excel.exe → splwow64.exe (the 32-bit print-spooler helper) is the standard Office pattern, seen on 298-312 hosts. cmd.exe/powershell.exe → conhost.exe and services.exe → svchost.exe are routine OS-level spawns present fleet-wide. ### Baseline Knowledge Captured

For this (synthetic) fleet: Office apps spawning script interpreters/LOLBins is rare (0-2 events, 1-2 hosts) against a normal baseline of thousands of events across hundreds of hosts for legitimate Office→helper-process pairs. A future hunt over real telemetry should look for the same shape of outlier -- Office/email clients as parents of powershell.exe, certutil.exe, mshta.exe, cscript.exe, wscript.exe -- rather than assuming these three exact pairs will recur.

### Lessons Learned

**What Worked Well:**
- Deterministic programmatic filtering (`event_count <= 5` in Python) to find the anomalies, rather than asking the LLM to scan the table for outliers -- ground truth from code, not model judgment.
- Once anomalies were pre-filtered, asking the LLM to restate each row *verbatim* before adding one sentence of analytical context kept its narrative accurate.

**What Could Be Improved:**
- First attempt asked the LLM to find AND transcribe low-frequency rows out of the full 18-row table in one pass. It correctly found all 3 anomalies and got the process names and event_counts right, but fabricated the `distinct_host_count` value for all three -- each fabricated number was actually copied from an unrelated row elsewhere in the same table (e.g. it wrote `winword.exe,powershell.exe,1,265` -- the `265` belongs to a completely different row, `explorer.exe,powershell.exe,290,265`). This happened even though the model was given the real data and explicitly told not to invent anything -- grounding reduced but did not eliminate the error.
- Fix: never ask the model to search-and-transcribe multi-column data from a long context in one step. Filter/aggregate with code first, hand the model only the pre-filtered rows, and ask it to echo them back verbatim rather than reformat/summarize from memory. Confirmed this eliminated the transcription error on retry (see H-0034 dev notes).
