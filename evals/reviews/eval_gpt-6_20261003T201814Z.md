### 2.1 VShell: a stale port from a months-old sighting scopes the C2 rule (verified; regression)

`vshell-fake-resume/rules/network_connection__connection_to_an_address_or_host_named_in_the_source_intelli.yml`:

```yaml
selection_1_40010: {DestinationIp: 38.207.178.192, DestinationPort: 40010}
```

`source.txt` line 525: "MEDIUM confidence 38.207.178[.]192:40010 ThreatFox-derived VShell sighting, 2026-04-15",
and the report calls it "secondary-source evidence, not a campaign bridge". This sample used 50812 and 50813 only.
`core/provenance.py` states the rule it breaks: "an old service port (H-0618's `:40010`) never scopes a current
rule". The cause is `attach_text_ports`, added 2026-10-03, which attaches every `address:port` the page writes,
whatever the sentence says about it. The same function put ports 80 and 8081 on the Redis C2 (2.6). The gold set
has no check for it.

### 2.2 Redis: the operator's machine is still described as the victim's in the draft's own prose (verified)

`redis-cryptomining-botnet/draft.md`, ABLE Evidence:

> execution of Python scripts (c2_persist.py, deploy_all.py [the source does not tie it to this intrusion
> (attacker-side)]) with network connections to known C2 infrastructure

`c2_persist.py` is the C2 server itself, on the operator's Windows host ("launches the operator's C2 server
component directly"); only `deploy_all.py` was flagged. "What Suspicious Looks Like" lists `c2_persist.py` and
`python.exe` for a Linux hunt. The gold `windows-artifacts` pattern is `xmrig\.exe|powershell|%temp%`, so
`python.exe` passes.

The Primary Source Evidence table marks 15 of the operator's own files `active`, among them `exploit_wp.py`,
`wp_spray.py`, `wp_scan_results.json`, `SAM.save`, `SYSTEM.save`, `rogue_result.txt` and
`C:/host_public/run_launch.b64`. Their sentences never say "operator", so the attacker-side wording rule does not
reach them. No rule was built on them in this run, but they stay in the list of values the model may use.

### 2.3 Redis: the Location names the wrong ports (verified)

### 2.4 Redis: `ayakliborsa.net` is typed C2 and given high-severity DNS rules without support (verified)

Indicator table: "`ayakliborsa.net` | domain | c2 | active" and "`socket.ayakliborsa.net` | hostname | c2 | active".
The deterministic DNS rule (level high) matches both names and every subdomain (`.ayakliborsa.net`).

The report says the hostname is operator-controlled, served on port 8081, and "the string ayakliborsa never appears

### 2.5 macOS and VShell: the draft tells the reader the main artifact is not part of the intrusion (verified)

`vshell-fake-resume/draft.md` does the same to the decoy: "removed (observables): "C:\Windows\Temp\Beijing Institute
of Technology_..._personal resume (2).docx" - the source does not tie it to this intrusion (unknown)", while a

### 2.6 Redis: network rule covers ports and an address victims do not contact (verified)

The `network_connection` rule has selections for `188.245.99.156` on ports 80 and 8081, and for `45.155.102.89` on

### 2.7 macOS: a rule that cannot match (verified)

`process_creation__command_the_source_shows_being_run_mkdir_p_library_caches_co.yml`:

```yaml
selection: {Image|endswith: /mkdir, CommandLine|contains: '-p /Library/Caches/com.apple.trustd'}
```

The source command is `mkdir -p "$HOME/Library/Caches/com.apple.trustd"`. Stripping `$HOME` left `-p` directly
before `/Library`; a real command line reads `-p /Users/<name>/Library/...`, so the string never occurs.

### 2.8 VShell: the decoy and "resume" rules use the report's English translation (suspected)

### 2.9 Redis: no rule for the miner running, the check-in request, or Redis writing cron files (verified)

- The report prints the miner's command line: `/tmp/.xmrig --no-color --donate-level=1 --url=pool.moneroocean.stream:443
  --tls ...`. No `process_creation` rule matches `Image: /tmp/.xmrig` or those arguments. Command rules cover only a
  fixed list of programs, and `hidden-miner` passes on the file rule alone.
- The check-in is "a GET of the form /ping?h=<hostname>". The template URL was dropped as not a URL, and its path
  went with it; no proxy rule has `/ping?h=`.
- The one behavioural rule the model attempted was rejected: `trail.log`, "rejected process_creation: '/redis-server'
  is not a value the source gives". `redis-server` writing under `/etc/cron.d` or connecting out to a non-Redis port
  is the general detection for this technique, and the exact-values rule forbids it because the report never spells
  the binary's name.
- `trail.log`: "the source publishes no detection guidance section". The report has one, "Detection and Mitigation
  Recommendations", with usable items ("audit /etc/cron.d/, /etc/cron.hourly/, /etc/crontab, and /var/spool/cron/ for
  entries referencing curl, tar, or xmrig").

### 2.14 Additional coverage defects (verified)

- **VShell prose conflates the decoy with the payload path.** `draft.md`, ABLE
  Scoping, says the stager downloads and decodes VShell "via a decoy DOCX".
  `source.txt` describes the DOCX as the lure/decoy and separately says the
  stager downloads the RAT payload over the network. The DOCX does not deliver
  the RAT. The gold checks that require the chain's facts do not reject this
  contradictory relationship.
- **VShell network rule has an unsupported Word exclusion.**
  `rules/network_connection__suspicious_c2_beaconing_to_known_malicious_ip_on_non_standar.yml`
  contains `Image|endswith: \\winword.exe` under `filter_legitimate`. The
  source associates C2 traffic with the infection stages, not Word; the
  exclusion can suppress a matching network event with a Word image and has
  no source grounding.
- **macOS proxy suffix drops the query string.**
  `rules/proxy__request_for_a_url_path_named_in_the_source_intelligence.yml`
  matches `/92392991a0cca55` with `c-uri|endswith`; the source command in
  `source.txt` uses `http://193.29.224[.]151/92392991a0cca55?force=1`. Proxy
  records retaining the query string will not end with the configured path.
- **macOS T1684 is name-matched.** `draft.md`'s Technique Evidence row quotes
  only "A sophisticated macOS malware campaign leverages ClickFix social
  engineering" and gives no observed system behavior. That is technique-name
  recognition rather than evidence. The primary report separately describes
  `osascript` prompts, but the gold set's observed list does not include
  T1059.002 (AppleScript), leaving that described behavior outside technique
  recall.
- **Redis `mv` rule uses a shell-expanded wildcard literally.**
  `rules/process_creation__command_the_source_shows_being_run_mv_tmp_xmrig_xmrig.yml`
  matches `CommandLine|contains: /tmp/xmrig-*/xmrig`. In the cited command the
  shell expands `/tmp/xmrig-*` before invoking `mv`; the process command line
  receives a concrete directory name, not the asterisk. This rule cannot
  match the described invocation.

## 3. Problems with the gold sets and the scorer

1. **`any_of` detections are satisfied by the weakest alternative.** Redis `cron-written` passed without a rule for the
   primary path (the known file-name collision removed it) because `/etc/cron.d/redis-update` matches. `hidden-miner`
   passes on a file rule with no process rule. macOS `launch-agent` passes on any `launchctl bootstrap`.
2. **No gold set forbids a port.** 2.1 and 2.6 would each need a `forbid` on `network_connection.DestinationPort`
   paired with the address; the indicator checks test a value in a field, not a pair.
3. **Redis gold is silent on the attacker-side material it was written to test.** It forbids one target address and
   two hashes. It has no check for `ayakliborsa.net`, for operator files in rules, or for T1213.006, T1059.006 and
   T1620 (unreviewed, so free).
4. **Claim patterns are literal.** "wallet theft", "defense-related research" and `python.exe` all pass (2.12, 2.2).
5. **The Technique Evidence table is still scored as the draft's prose.** It can quote the model-written research
   document; an earlier VShell run failed `persistence-as-fact` on such a quote.
6. **VShell gold does not list T1571.** The pipeline now maps it from the report's 50812/50813 ports; it is reported
   as unreviewed. It belongs in `acceptable`.
7. **The Redis report disagrees with itself on the primary path.** Prose: "/etc/cron.d/.redis-miner". IOC table:
   "/etc/cron.d/redis-miner". The report also says cron skips dotfiles in `cron.d`. The gold regex accepts both, which
   is right, but a comment should say why.
8. **The scorer cannot tell whether a rule can match.** 2.7 and 2.8 are rules that exist and are credited or ignored
   on their field names alone.
9. **Gold technique denominator omits described AppleScript behavior.** The
   macOS source describes an `osascript` dialog prompting for credentials,
   but the gold's observed technique list does not include T1059.002. The
   draft happens to map it, but technique recall does not measure that
   behavior.
10. **Redis gold is silent on QA indicators and fallback persistence.** The
    source distinguishes QA-target addresses such as `47.250.92.230` from
    victim infrastructure and lists `/etc/apt/apt.conf.d/99sys-update` and
    `/etc/profile.d/sys-init.sh` as persistence paths. No gold checks reject
    QA addresses as campaign IOCs or require these fallbacks.
11. **The Redis download detection requires endpoint process evidence.** The
    `xmrig-download` check requires process-creation fields for `curl` and
    `xmrig`, supported by the report's quoted `curl` command. The proxy rule
    is complementary evidence and should not substitute for endpoint process
    coverage.
