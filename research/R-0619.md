## 1. System Research: How It Works

### Summary
Kubernetes audit logs capture API-level interactions, such as user actions and resource modifications, but do not provide visibility into processes or behaviors inside containers. To gain runtime context, audit logs must be correlated with container runtime data using shared identifiers like pod names and namespaces within a synchronized time window. This correlation is essential for detecting anomalies like container escapes that are invisible to audit logs alone.

### Key Findings
- Kubernetes audit logs include the `user.name` field (e.g., `system:serviceaccount:`) to identify API principals, enabling tracking of user or service account activity across API calls.
- Audit logs alone cannot detect process-level activities inside pods, such as commands executed via `kubectl exec`, because they only record the API request, not the runtime behavior within the container.
- Container runtime data, such as process events and network activity, must be queried using pod names and namespaces from audit logs to establish a timeline of suspicious behavior.
- Container runtime logs (stdout/stderr) are unreliable under adversarial conditions, as a compromised container may hide or manipulate its own logs.
- A container escape event may be detected only when audit logs are correlated with runtime telemetry, as the escape itself may not appear in audit logs but will manifest in process or network anomalies.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries exploit the gap between Kubernetes API-level audit logs and container runtime data by performing actions that bypass direct process monitoring, such as container escapes, which may not be visible in traditional EDR or process logs. This allows them to execute malicious activity within the cluster without being detected by runtime tools that only observe process execution on the host.

### Key Findings
- Kubernetes audit logs and container runtime data must be correlated to detect attacks that exploit identity-driven behaviors and privilege escalation within the cluster.
- A critical indicator of compromise is a container escape that does not appear in process execution logs, indicating a discrepancy between API-level actions and runtime behavior.
- Tools like Wazuh and Cortex Cloud enable correlation of Kubernetes audit events with telemetry from the control plane, runtime, and cloud IAM to detect advanced attack patterns.
- Full-stack visibility across cloud APIs, Kubernetes audit events, node telemetry, and container runtime is essential for understanding attack progression.
- Standardized formats such as ECS and OpenTelemetry facilitate correlation across diverse data sources, improving detection accuracy.
- EDR tools often fail to map process IDs on the host back to specific containers, pods, or namespaces, creating blind spots in detection [UNCERTAIN]

## 3. Telemetry Mapping: OCSF Fields

### Summary
The source intelligence describes an adversary behavior involving a container escape that is detectable by correlating Kubernetes audit logs with container runtime data. The behavior includes a process running inside a pod that should not exist, which is revealed when Kubernetes API audit logs show a pod creation or exec request, but container runtime telemetry (e.g., from containerd or CRI-O) shows a process running outside the expected pod context. The key indicator is a discrepancy between the API surface (which reports normal activity) and the runtime surface (which reveals unauthorized execution). This escape is detected via two specific fields: one that links the Kubernetes API request to the container ID (via `k8s.pod.name` and `container.id`), and another that exposes the actual process path and PID in the container runtime data (`process.file.path` and `process.pid`). The field `process.file.path` is particularly critical because it can reveal execution of unexpected binaries (e.g., `/bin/sh` or `/usr/bin/docker`) in a context where such behavior should not occur.

### Key Fields

OCSF path → the event field `knowledge/environment.md` documents for it.

- `process.file.path` → unmapped: the environment profile documents no field: Captures the actual binary path executed inside the container, which can reveal unauthorized or unexpected processes during an escape.
- `process.pid` → unmapped: the environment profile documents no field: Provides the process ID from the container runtime, enabling correlation with process creation events and identifying out-of-context execution.
- `process.cmd_line` → `command_line` (Endpoint): Captures the full command line of the process, which may reveal suspicious or elevated execution patterns (e.g., `sh -c` or `docker exec`) not aligned with normal pod behavior.

## 5. Research Synthesis

### Executive Summary
Correlating Kubernetes audit logs with container runtime data enables detection of container escapes that evade traditional process monitoring by identifying discrepancies between API-level actions (e.g., pod exec) and actual runtime behavior (e.g., unexpected process execution outside pod context). Critical indicators include mismatches in `k8s.pod.name` and `container.id` alignment, and the presence of `process.file.path` for unauthorized binaries such as `/bin/sh` or `/usr/bin/docker` in non-pod contexts.

### Recommended Hypothesis
> Adversaries use container escapes that bypass process-level visibility by executing malicious binaries within a pod context, yet manifest outside the expected runtime scope, to maintain persistence and evade detection on Kubernetes clusters.

### Gaps Identified
- The absence of consistent correlation between `k8s.pod.name` in audit logs and `container.id` in container runtime telemetry creates blind spots for detecting escapes that occur post-execution but outside expected pod boundaries.
- Lack of real-time synchronization between Kubernetes audit logs and container runtime process telemetry (e.g., `process.file.path`, `process.pid`) prevents timely detection of out-of-context execution, especially when logs are manipulated or obscured.

### Key Findings
- Hypothesis: Adversaries use container escapes that bypass process-level visibility by executing malicious binaries within a pod context, yet manifest outside the expected runtime scope, to maintain persistence and evade detection on Kubernetes clusters.
- Gap: The absence of consistent correlation between `k8s.pod.name` in audit logs and `container.id` in container runtime telemetry creates blind spots for detecting escapes that occur post-execution but outside expected pod boundaries.
- Gap: Lack of real-time synchronization between Kubernetes audit logs and container runtime process telemetry (e.g., `process.file.path`, `process.pid`) prevents timely detection of out-of-context execution, especially when logs are manipulated or obscured.
- Focus: Implement cross-layer telemetry correlation using shared identifiers (`pod.name`, `namespace`, `container.id`) within a synchronized time window to detect anomalies where API actions do not align with actual process execution.
- Focus: Instrument container runtime data sources (e.g., containerd, CRI-O) to capture and enrich `process.file.path` and `process.cmd_line` for all process creation events, enabling detection of unexpected binaries in pod-external contexts.
- Focus: Deploy detection logic that flags `process.file.path` entries (e.g., `/bin/sh`, `/usr/bin/docker`) when associated with a `container.id` not matching the `k8s.pod.name` from the corresponding audit log entry, indicating a potential escape.
