## 1. System Research: How It Works

### Summary
Legitimate remote management workflows involve the execution of ScreenConnect installers (e.g., ScreenConnect.ClientSetup.exe) to establish encrypted connections between client devices and authorized relay infrastructure for administration. From a sensor perspective, this typically manifests as specific binary hashes communicating with known vendor domains or IP ranges associated with ConnectWise/ScreenConnect services.

### Key Findings
- The primary payload is identified as ScreenConnect.ClientSetup.exe (SHA256: 41d2097e8ac636a478aa011e12128c03b3b9bb3c8efca43d3c4f214ac8b1f07b) and its service variant ScreenConnect.ClientService.exe (SHA256: 9f5910d69a4fbc56ff1854e7e0df3199fbfddd7fe6b374f7d816fa6ae70ef991), which establish persistence via Windows services.
- Defense evasion tactics include the execution of custom binaries named HideCursor.exe and HideUL.exe to conceal attacker activities, alongside the use of Browser-in-the-Browser (BiTB) techniques to mimic legitimate Adobe Reader update prompts.
- Network telemetry indicates communication with rogue relay infrastructure such as relay.goldenmelon.us, relay.illuminantgroup.net, and scx.illuminantgroup.net, as well as direct connections to attacker-controlled IPs like 144.172.115.59 on port 8041.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Sophisticated adversaries are leveraging Browser-in-the-Browser (BiTB) phishing techniques to deceive users into downloading rogue ScreenConnect Remote Management tools disguised as legitimate software updates, such as Adobe Reader patches. These campaigns establish redundant persistent access through multiple rogue RMM instances and utilize defense-evasion binaries to conceal attacker activities on compromised endpoints.

### Key Findings
- Attackers employ BiTB lures that mimic legitimate browser popups (e.g., fake Adobe update prompts or CAPTCHA screens) hosted on domains like adoube.vu and selectstructure.com.au to bypass user awareness training.
- The primary payload consists of rogue ScreenConnect installers (ScreenConnect.ClientSetup.exe/MSI) downloaded from attacker-controlled infrastructure, including hosthiifran.screenconnect.com and wir.consultingics.com.
- Threat actors establish redundant persistence by deploying multiple rogue ScreenConnect instances simultaneously, utilizing Windows services for continued remote access and connecting to C2 domains such as relay.goldenmelon.us.
- Defense-evasion binaries HideCursor.exe and HideUL.exe are executed post-compromise to hide attacker activities, with file hashes including f048400c... and fc96a04c... identified in VirusTotal as associated with Connectwise Control/ScreenConnect.
- Indicators of Compromise (IOCs) include specific SHA256 hashes for the rogue ScreenConnect clients (e.g., 9f5910d6..., f048400c...) and URLs containing query parameters mimicking legitimate access tokens.

## 5. Research Synthesis

### Executive Summary
Sophisticated phishing campaigns utilize Browser-in-the-Browser (BiTB) lures to deliver rogue ScreenConnect installers disguised as legitimate software updates, establishing redundant service-based persistence and executing custom defense-evasion binaries (HideCursor.exe, HideUL.exe) to conceal remote access activities. Detection requires correlating specific executable hashes with anomalous network connections to non-standard relay infrastructure, such as relay.goldenmelon.us, rather than relying solely on known vendor domains.

### Recommended Hypothesis
> Adversaries use Browser-in-the-Browser phishing lures and rogue ScreenConnect installers to establish redundant remote management persistence and execute defense-evasion binaries on Windows endpoints to maintain covert access.

### Gaps Identified
- Standard endpoint detection may miss these threats if it only whitelists known ConnectWise/ScreenConnect domains, as this campaign uses attacker-controlled relays (e.g., wir.consultingics.com, relay.goldenmelon.us) and custom filenames (AdbRdBkUpsStUp.msi) that bypass domain-based allowlists.

### Key Findings
- Hypothesis: Adversaries use Browser-in-the-Browser phishing lures and rogue ScreenConnect installers to establish redundant remote management persistence and execute defense-evasion binaries on Windows endpoints to maintain covert access.
- Gap: Standard endpoint detection may miss these threats if it only whitelists known ConnectWise/ScreenConnect domains, as this campaign uses attacker-controlled relays (e.g., wir.consultingics.com, relay.goldenmelon.us) and custom filenames (AdbRdBkUpsStUp.msi) that bypass domain-based allowlists.
- Focus: Implement strict file integrity monitoring for the creation of Windows services associated with ScreenConnect.ClientService.exe variants in non-standard user directories (e.g., C:\Users\<User>\Documents\ScreenConnect\Temp\) and alert on outbound connections to IP 144.172.115.59 or unrecognized relay hosts.
- Focus: Deploy behavioral monitoring for the execution of HideCursor.exe and HideUL.exe, and correlate their presence with the immediate deployment of ScreenConnect.ClientSetup.exe to identify the post-exploitation evasion phase of the attack chain.
