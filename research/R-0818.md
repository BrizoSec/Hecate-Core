## 1. System Research: How It Works

### Summary
The Lunex malware campaign utilizes a Bring Your Own Vulnerable Driver (BYOVD) technique, specifically exploiting CVE-2023-20598 in the AMD PDFWKRNL.sys driver, to disable endpoint security monitoring by zeroing kernel callbacks. This allows the deployment of LunexStealer, which persists via registry keys, scheduled tasks, and Native Messaging Hosts while stealing credentials from browsers and cryptocurrency wallets.

### Key Findings
- The malware exploits AMD's PDFWKRNL.sys driver (CVE-2023-20598) to dynamically identify and zero security-related kernel callbacks by retrieving Windows kernel debugging symbols from Microsoft's Symbol Server, enabling version-agnostic evasion of endpoint protection.
- Persistence is established through multiple mechanisms including the registry key 'com.lunex.explorer', a scheduled task named 'psychedelicloveUtils', and Native Messaging Host registrations, ensuring continued access even if the primary executable is deleted.
- The attack infrastructure relies on a staging domain 'uasputnik.com' hosting fake CAPTCHA lures in Ukrainian to deliver the initial loader, which subsequently deploys LunexStealer to harvest credentials from seven Chromium-based browsers and cryptocurrency wallets.

## 5. Research Synthesis

### Executive Summary
The Lunex campaign leverages the AMD PDFWKRNL.sys driver (CVE-2023-20598) to execute a Bring Your Own Vulnerable Driver (BYOVD) attack, dynamically zeroing security-related kernel callbacks via symbol server lookups to blind endpoint detection without terminating EDR processes. This evasion enables the deployment of LunexStealer, which harvests browser and cryptocurrency credentials while maintaining robust persistence through Native Messaging Host registrations and scheduled tasks that survive primary executable deletion.

### Recommended Hypothesis
> Adversaries use kernel callback manipulation via AMD PDFWKRNL.sys to disable security monitoring and deploy credential stealing malware on Windows endpoints targeting Ukrainian users.

### Gaps Identified
- Standard EDR telemetry often fails to detect the zeroing of kernel callbacks in memory, as the malicious driver appears legitimate and does not trigger standard process creation alerts for the disabling action itself.
- Detection is hindered by the use of Microsoft's official Symbol Server to dynamically resolve function addresses, allowing the malware to bypass static signatures for known vulnerable driver offsets and operate version-agnostically.

### Key Findings
- Hypothesis: Adversaries use kernel callback manipulation via AMD PDFWKRNL.sys to disable security monitoring and deploy credential stealing malware on Windows endpoints targeting Ukrainian users.
- Gap: Standard EDR telemetry often fails to detect the zeroing of kernel callbacks in memory, as the malicious driver appears legitimate and does not trigger standard process creation alerts for the disabling action itself.
- Gap: Detection is hindered by the use of Microsoft's official Symbol Server to dynamically resolve function addresses, allowing the malware to bypass static signatures for known vulnerable driver offsets and operate version-agnostically.
- Focus: Monitor for `PDFWKRNL.sys` file creation or loading events in system directories alongside unusual HTTP/S traffic to `msdl.microsoft.com` for symbol downloads, indicating dynamic kernel address resolution.
