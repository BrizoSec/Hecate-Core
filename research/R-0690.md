## 1. System Research: How It Works

### Summary
Zimbra Collaboration Suite processes SNMP notifications via the 'swatchdog' utility, which invokes 'snmptrap' to handle system state changes triggered by health monitoring. Under normal operation, this path sanitizes input to prevent shell command execution, but exploitation occurs when untrusted SMTP data bypasses this validation, allowing arbitrary commands to run as the 'zimbra' service account.

### Key Findings
- The vulnerability exists in the SNMP notification processing logic where 'swatchdog' incorporates attacker-controlled values into a 'snmptrap' shell invocation without sufficient sanitization.
- Exploitation requires two specific environmental conditions: the optional 'zimbra-snmp' package must be installed, and SNMP notifications must be explicitly enabled on the server.
- The attack vector is unauthenticated; it relies on sending a specially crafted SMTP request to internet-facing mail servers, requiring no user interaction or valid credentials to trigger command execution.
- Successful exploitation grants initial access as the 'zimbra' service account, which attackers leverage to deploy JSP webshells in Jetty/mailboxd directories and escalate privileges via PAM configuration abuse.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries exploit CVE-2026-73570, an unauthenticated OS command injection in the Zimbra SNMP notification path, to gain initial access and execute arbitrary commands. Following exploitation, they employ masquerading techniques (T1036.005) by deploying JSP web shells with legitimate names in trusted directories and creating systemd services that mimic Zimbra logging components to maintain persistence.

### Key Findings
- The vulnerability CVE-2026-73570 allows unauthenticated command execution via specially crafted SMTP requests targeting the SNMP notification path when the optional zimbra-snmp package is installed.
- Attackers deployed JSP web shells in Jetty and mailboxd application paths, using legitimate filenames to evade detection, and utilized wget/curl for payload delivery.
- Persistence was established through a systemd service named 'zimlog.service' in /etc/systemd/system/, with timestamps modified to match legitimate services like rsync.service and sshd.service.
- Privilege escalation to root was achieved by abusing Zimbra’s sudo-authorized helpers, specifically manipulating PAM configurations via a symlinked log file to gain unrestricted sudo access for the zimbra account.
- Lateral movement across the cluster was automated using Zimbra’s existing SSH identity (/opt/zimbra/.ssh/zimbra_identity) and rsync to distribute webshells and payload fragments to peer nodes.

## 5. Research Synthesis

### Executive Summary
Microsoft Threat Intelligence tracked exploitation of CVE-2026-73570, an unauthenticated command injection in Zimbra's SNMP path, where adversaries leveraged masquerading (T1036.005) to deploy JSP webshells and a systemd service named 'zimlog.service' with manipulated timestamps to evade detection. The campaign included sophisticated privilege escalation via PAM configuration abuse to gain root access, followed by lateral movement using Zimbra's SSH identity and credential harvesting from zmlocalconfig.

### Recommended Hypothesis
> Adversaries use timestamp manipulation of systemd service files and legitimate naming conventions (T1036.005) to establish persistence via 'zimlog.service' on compromised Zimbra mail servers.

### Gaps Identified
- Lack of telemetry for file metadata modification events (specifically utime/utimensat syscalls or 'touch' command execution in /etc/systemd/system/) allows adversaries to blend malicious services with legitimate system artifacts like sshd.service.
- Insufficient monitoring of PAM configuration changes (symlink creation in /etc/pam.d/sudo) and subsequent privilege escalation via pam_exec hooks, which enables the transition from zimbra user to root without triggering standard sudo alerting if NOPASSWD entries are pre-existing or subtly modified.

### Key Findings
- Hypothesis: Adversaries use timestamp manipulation of systemd service files and legitimate naming conventions (T1036.005) to establish persistence via 'zimlog.service' on compromised Zimbra mail servers.
- Gap: Lack of telemetry for file metadata modification events (specifically utime/utimensat syscalls or 'touch' command execution in /etc/systemd/system/) allows adversaries to blend malicious services with legitimate system artifacts like sshd.service.
- Gap: Insufficient monitoring of PAM configuration changes (symlink creation in /etc/pam.d/sudo) and subsequent privilege escalation via pam_exec hooks, which enables the transition from zimbra user to root without triggering standard sudo alerting if NOPASSWD entries are pre-existing or subtly modified.
- Focus: Hunt for file integrity anomalies in /etc/systemd/system/ where service file timestamps differ significantly from their inode creation time or deviate from known baseline system service patterns.
