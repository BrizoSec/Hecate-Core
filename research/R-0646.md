## 1. System Research: How It Works

### Summary
AMOS stealer operates by deceiving users into executing a Zsh script that downloads and installs a Mach-O binary, which then harvests sensitive data including Keychain credentials, browser cookies, and cryptocurrency wallet files. The infected host establishes persistent access via LaunchDaemons and exfiltrates the collected data compressed in an out.zip archive through HTTP POST requests to command-and-control servers.

### Key Findings
- The malware installer binary is temporarily saved as /tmp/helper, while a plist file at /tmp/starter indicates persistence mechanisms creating hidden files like .service in /Library/Application Support/.com.apple.accountsd/ and . in /Library/Application Support/.com.apple.metadata.mds/.
- Command and control communication primarily involves HTTP POST requests to the active IP 161.35.146.120, with historical traffic also observed to 188.166.78.138.
- Persistence is achieved by installing a root-level LaunchDaemon named com.finder.helper, ensuring the malware survives reboots and process termination.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
The Atomic macOS (AMOS) Stealer targets users by distributing malware disguised as legitimate installation guides or cracked applications, utilizing deceptive setup instructions to trick victims into executing malicious shell commands. Once executed, the malware exfiltrates sensitive data including credentials, browser information, and cryptocurrency wallets while employing evasion techniques such as virtualization checks and XOR encoding.

### Key Findings
- Adversaries use deceptive staging domains like getmacouscloud[.]com to host fake installation instructions for macOS toolkits, tricking users into executing commands that download the initial Z-shell script from ferncore13[.]com.
- The malware employs a multi-stage execution process involving an installer saved as /tmp/helper and a persistent binary stored in /Library/Application Support/.com.apple.accountsd/ under a .service file to maintain access.
- AMOS Stealer exfiltrates sensitive user data by collecting information from the Desktop, Documents, and Notes applications, as well as browser credentials and cryptocurrency wallet files, compressing them into out.zip in the /tmp directory.
- The stealer utilizes Command and Control (C2) infrastructure via HTTP POST requests to IPs such as 161.35.146[.]120 and historical addresses like 188.166.78[.]138, alongside URLs on grove-89[.]com for metrics tracking.
- Detection relies on identifying specific SHA-256 hashes of the malicious artifacts, including the initial Zsh script (71781ad...), the extracted payload (7ea6ff8...), the installer (a598fcd...), and persistent binaries (6bfcdb4...).

## 3. Telemetry Mapping: OCSF Fields

### Summary
The AMOS stealer activity involves a multi-stage execution chain starting with a deceptive macOS setup guide hosted on getmacouscloud.com. The attacker uses curl to download an initial Zsh script from ferncore13.com, which then extracts and executes further payloads. These actions result in the creation of Mach-O binaries and helper files in /tmp and /Library/Application Support, establishing persistence via plist configurations. Post-exploitation involves credential/data exfiltration to C2 servers (161.35.146.120 and 188.166.78.138) via HTTP POST requests, often with data compressed into out.zip.

## 5. Research Synthesis

### Executive Summary
Atomic macOS (AMOS) Stealer executes a multi-stage compromise by deceiving users into running Zsh scripts that download Mach-O binaries, establishing persistence via hidden files in /Library/Application Support and LaunchDaemons. The malware harvests credentials, browser cookies, and crypto wallets from the host, compressing them into out.zip for exfiltration to C2 infrastructure over HTTP POST.

### Recommended Hypothesis
> Adversaries use deceptive staging domains and Zsh script execution to install persistent Mach-O binaries that harvest user data and exfiltrate it via HTTP POST to C2 servers on macOS hosts.

### Gaps Identified
- Current telemetry lacks visibility into the creation of hidden files (e.g., .service, .) within /Library/Application Support directories, allowing persistence mechanisms to remain undetected by standard directory monitoring.
- Network detection fails to identify the specific HTTP POST payload structure used for exfiltrating out.zip archives, as generic web traffic monitoring may not distinguish stealer beaconing from legitimate API metrics calls to domains like grove-89.com.

### Key Findings
- Hypothesis: Adversaries use deceptive staging domains and Zsh script execution to install persistent Mach-O binaries that harvest user data and exfiltrate it via HTTP POST to C2 servers on macOS hosts.
- Gap: Current telemetry lacks visibility into the creation of hidden files (e.g., .service, .) within /Library/Application Support directories, allowing persistence mechanisms to remain undetected by standard directory monitoring.
- Gap: Network detection fails to identify the specific HTTP POST payload structure used for exfiltrating out.zip archives, as generic web traffic monitoring may not distinguish stealer beaconing from legitimate API metrics calls to domains like grove-89.com.
- Focus: Monitor for the creation of Mach-O binaries in /tmp and subsequent execution processes that write to hidden directories under /Library/Application Support/.com.apple.*.
