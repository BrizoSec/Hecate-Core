## 1. System Research: How It Works

### Summary
Redis operates as an in-memory data structure store that, when misconfigured without authentication or restricted network access, allows unauthenticated clients to execute administrative commands such as CONFIG SET dir. This normal functionality was exploited via rogue replication to write malicious cron jobs and binaries to persistent system locations, bypassing the need for software-specific vulnerabilities.

### Key Findings
- The attack leveraged Redis's native replication feature (MASTERAUTH/REPLCONF/PSYNC) to inject a crafted RDB blob that wrote a malicious cron job to /etc/cron.d/.redis-miner and deployed an XMRig binary to /tmp/.xmrig.
- Compromised systems established persistent connections to the Monero mining pool at pool.moneroocean.stream:443 over TLS using the hidden /tmp/.xmrig executable, indicating active cryptocurrency exfiltration.
- The operator utilized a C2 infrastructure at 188.245.99.156 (port 10000) for persistence checks via HTTP GET requests to c2_persist.py, logging results in a local SQLite database named c2_persist.db.
- Victims spanned Redis versions 2.8.17 through 7.2.0 on various Linux distributions, confirming the compromise was driven by missing authentication (no-auth) rather than version-specific CVEs.
- The operator's toolkit contained Python scripts probing for web roots (/var/www/html, /usr/share/nginx/html) and SSH directories (/home/ubuntu/.ssh, etc.), though only the Redis/cron vector achieved confirmed compromises in this campaign.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries exploited unauthenticated Redis instances across versions 2.8.17 to 7.2.0 using rogue replication techniques to inject malicious cron jobs, resulting in the compromise of 3,562 servers for Monero cryptomining. The operator's extensive toolkit and campaign logs were accidentally exposed in an open directory, revealing the full scope of the operation and associated infrastructure.

### Key Findings
- The attack relies on Redis misconfiguration (missing authentication) rather than software vulnerabilities, allowing 'rogue replication' to write a cron job at /etc/cron.d/.redis-miner that deploys the XMRig miner to /tmp/.xmrig.
- Campaign logs confirm two distinct runs targeting 12,966 hosts, achieving compromises on 3,562 Redis servers, with additional tools designed to pivot via webshells or SSH key injection showing zero confirmed success in this campaign.
- The primary Command and Control (C2) infrastructure includes the active IP 188.245.99.156 hosting the toolkit and persistence scripts, while miners connect to pool.moneroocean.stream:443 over TLS using a hardcoded wallet.
- Hash indicators f90c8b1dcd374d4f552744ee1765583d (MD5) and 420c7850e09b7c2b9e39e2a93e204e3c56bcf08a685ff1daa986e3c348da5d2a (SHA256) identify artifacts from the exposed 147-file toolkit, which includes Python exploit source code and Windows registry hives.
- Wallet reuse links this operator to a separate February 2026 open directory at 194.48.248.105 containing Meterpreter and XMRig kits, extending the known activity timeline by five months and indicating broader malware distribution capabilities.

## 5. Research Synthesis

### Executive Summary
Adversaries leveraged unauthenticated Redis instances via rogue replication to inject a persistent cron job at /etc/cron.d/.redis-miner, deploying an XMRig cryptominer binary to /tmp/.xmrig and establishing C2 communication with pool.moneroocean.stream:443. The attack chain relies on configuration failures rather than software exploits, allowing the operator to target Redis versions 2.8.17 through 7.2.0 across diverse Linux distributions.

### Recommended Hypothesis
> Adversaries use rogue replication to inject malicious cron jobs and deploy hidden XMRig binaries to achieve persistent cryptomining on unauthenticated Redis servers

### Gaps Identified
- Lack of EDR telemetry monitoring for the creation of hidden files in /etc/cron.d/ or unexpected execution of binaries from /tmp/ on production servers
- Network detection blind spots regarding outbound TLS traffic to cryptocurrency mining pools (e.g., pool.moneroocean.stream) that may bypass standard port-based filtering due to use of port 443

### Key Findings
- Hypothesis: Adversaries use rogue replication to inject malicious cron jobs and deploy hidden XMRig binaries to achieve persistent cryptomining on unauthenticated Redis servers
- Gap: Lack of EDR telemetry monitoring for the creation of hidden files in /etc/cron.d/ or unexpected execution of binaries from /tmp/ on production servers
- Gap: Network detection blind spots regarding outbound TLS traffic to cryptocurrency mining pools (e.g., pool.moneroocean.stream) that may bypass standard port-based filtering due to use of port 443
- Focus: Hunt for Redis configuration anomalies where CONFIG SET dir allows write access to system directories like /etc/cron.d/ or /var/www/html
- Focus: Monitor for processes named xmrig or similar mining binaries running from temporary directories (/tmp) with outbound connections to known Monero pool IPs or domains
