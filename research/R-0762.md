## 1. System Research: How It Works

### Summary
Vidar information stealer employs a lightweight virtual machine executed via a bytecode interpreter to obfuscate strings, utilizing simple arithmetic primitives like XOR and rotation within a fetch-decode-execute loop. This VM mechanism works in tandem with per-build custom stream ciphers (ChaCha-based or ARX variants) to encrypt keys, nonces, and the actual string payloads, dynamically changing opcodes and constants to evade static analysis.

### Key Findings
- The malware implements a bytecode interpreter with a sparse 256-entry dispatch table containing only 14 active opcode handlers; undefined slots terminate execution, indicating a lightweight, accumulator-only VM architecture without stack or multi-register support.
- String obfuscation techniques evolved chronologically from basic XOR to ChaCha20, and finally to a hybrid approach in version 2.0+ where the VM decrypts keys/nonces for custom stream ciphers, with versions 2.2+ introducing ARX-based ciphers using FNV-1a hashing.
- Every build utilizes unique, per-build variations in opcodes, constants, substitution tables (S-boxes), and a hardcoded 4-byte XOR seed key, making automated static analysis significantly more difficult as the deobfuscation logic is not consistent across samples.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
The Vidar information stealer has evolved its string obfuscation techniques from basic XOR and ChaCha20 to a custom virtual machine and per-build stream ciphers, significantly hindering static analysis. These dynamic obfuscation methods allow the malware to change its code structure with every build, shifting detection challenges toward behavioral analysis rather than fixed signatures.

### Key Findings
- Vidar employs a lightweight bytecode interpreter with a custom virtual machine that uses 14 distinct opcodes (including XOR, addition, rotation, and substitution) to deobfuscate strings or decrypt keys/nonces for secondary encrypted data blocks.
- The malware utilizes per-build variations in its custom stream ciphers, specifically alternating between modified ChaCha-based designs and Add-Rotate-XOR (ARX) methods, ensuring that no two builds share identical encryption constants or lookup tables.
- This obfuscation strategy makes automated static analysis difficult, forcing defenders to rely on dynamic behavioral monitoring and process activity analysis rather than signature-based detection.
- The virtual machine operates via a fetch-decode-execute loop using a sparse 256-entry dispatch table, where the accumulator and XOR key are initialized with build-specific seed values that change frequently.
