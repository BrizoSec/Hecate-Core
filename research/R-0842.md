## 1. System Research: How It Works

### Summary
The Cisco Secure Firewall detects outbound connections from endpoints to external IPs, which are then enriched with threat intelligence and DNS filtering data to identify malicious domains hosted on shared CDN infrastructure. Analysts utilize AI-assisted triage and packet forensics to isolate the specific compromised host generating malicious traffic among many benign users sharing the same IP address. The incident is resolved by implementing precise DNS object blocks for the malicious domains at the perimeter, avoiding a broad IP block that would disrupt legitimate services.

### Key Findings
- Shared CDN infrastructure (Amazon CloudFront node 13.226.251.40) serves both legitimate enterprise applications (Samsung Health, Mindtickle, Amazon Video) and malicious C2 domains (moonlighthathel.org, ukankingwithea.com), making IP-based blocking ineffective.
- The primary threat indicator is CVE-2021-44228 (Log4j), associated with the malicious domains hosted on the shared IP, requiring domain-specific rather than network-layer mitigation.
- AI-assisted analysis combined with firewall logs and Endace packet forensics successfully isolated one unmanaged Intel laptop as the sole source of malicious traffic among 14 benign devices communicating with the same IP.
- Precision triage via DNS object blocks on Cisco Firepower Threat Defense neutralized the C2 communication without disrupting legitimate telemetry and streaming services for other attendees.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
The adversary abused a shared Amazon CloudFront CDN infrastructure (IP 13.226.251.40) to host malicious domains, leveraging the legitimate traffic of major services like Samsung Health and Amazon Video to mask C2 activity and avoid broad IP-based blocking. By targeting specific FQDNs rather than the underlying IP, the attacker attempted to evade detection while maintaining operational continuity for the compromised host.

### Key Findings
- The malicious infrastructure utilized a shared CDN node (13.226.251.40) associated with Amazon CloudFront, which simultaneously served benign services such as Samsung Health, Mindtickle, and Amazon Video, complicating precise triage.
- Two specific domains were identified as C2 indicators: moonlighthathel.org and ukankingwithea.com, both hosted on the same IP address to share infrastructure costs or evade simple reputation-based blocks.
- The threat was linked to CVE-2021-44228 (Log4j), suggesting the compromise may have resulted from exploitation of this widely known vulnerability on an unmanaged Intel laptop within the conference network.
- Analysts successfully isolated a single malicious device among 15 communicating with the IP by using AI-assisted triage and packet forensics, identifying one unmanaged Intel laptop as the source of malicious traffic.
- The response strategy employed precision DNS object blocks for the malicious domains at the perimeter (Cisco Firepower Threat Defense) rather than blocking the shared IP, thereby neutralizing the threat without disrupting legitimate traffic for other attendees.

## 5. Research Synthesis

### Executive Summary
This incident demonstrates the critical necessity of application-layer (DNS/HTTP) visibility over network-layer (IP) blocking when adversaries leverage shared CDN infrastructure to host C2 domains, as IP-based mitigation causes significant collateral damage to legitimate enterprise services. Effective triage requires correlating firewall logs with deep packet inspection or AI-assisted telemetry analysis to isolate specific compromised endpoints generating malicious traffic among benign users sharing the same upstream IP.

### Recommended Hypothesis
> Adversaries use shared CDN infrastructure to host malicious C2 domains, blending with legitimate high-reputation traffic to evade IP-based reputation blocks and complicate precise endpoint isolation.

### Gaps Identified
- Lack of granular DNS query logging correlated with specific source endpoints prevents rapid identification of the single compromised host among many benign users sharing a common CDN IP; reliance on IP-level indicators leads to false positives or unnecessary broad blocking.
- Inability to distinguish between legitimate application telemetry (e.g., Samsung Health, Amazon Video) and malicious C2 beaconing based solely on destination IP reputation scores, requiring deep packet inspection or behavioral analysis of the payload content rather than static IOCs.

### Key Findings
- Hypothesis: Adversaries use shared CDN infrastructure to host malicious C2 domains, blending with legitimate high-reputation traffic to evade IP-based reputation blocks and complicate precise endpoint isolation.
- Gap: Lack of granular DNS query logging correlated with specific source endpoints prevents rapid identification of the single compromised host among many benign users sharing a common CDN IP; reliance on IP-level indicators leads to false positives or unnecessary broad blocking.
- Gap: Inability to distinguish between legitimate application telemetry (e.g., Samsung Health, Amazon Video) and malicious C2 beaconing based solely on destination IP reputation scores, requiring deep packet inspection or behavioral analysis of the payload content rather than static IOCs.
- Focus: Implement DNS object-level blocking policies for identified malicious FQDNs while maintaining allow-lists for shared CDN IPs to preserve service availability during active incidents.
