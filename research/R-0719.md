## 1. System Research: How It Works

### Summary
The OAuth 2.0 device authorization grant flow (RFC 8628) is a legitimate authentication mechanism designed for devices lacking standard input capabilities, such as IoT gadgets or smart TVs, allowing them to obtain tokens by having the user authorize via a secondary device. In this context, it functions normally by generating a unique user code and verification URI that the victim must visit to complete the handshake.

### Key Findings
- The GhostCode campaign specifically abuses the Microsoft Authentication Broker application ID (29d9ed98-a469-4536-ade2-f981bc1d605e), which is normally used for legitimate IoT and smart TV integrations, to hijack Microsoft 365 accounts.
- Upon successful authentication via the device code flow, threat actors register three new devices and harvest Primary Refresh Tokens within 78 seconds, granting them near-single sign-on access for up to 14 days.
- The attack infrastructure utilizes residential proxy rotation to distribute the phishing kit and mask the origin of token usage, making detection through standard IP-based telemetry difficult.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries utilize the 'GhostCode' phishing kit to exploit Microsoft's OAuth 2.0 device authorization grant flow, tricking victims into authenticating attacker-controlled devices via lookalike domains and obfuscated HTML files. This technique allows threat actors to bypass multi-factor authentication and obtain Primary Refresh Tokens for persistent access to Microsoft accounts.

### Key Findings
- GhostCode abuses the OAuth 2.0 device authorization grant flow to obtain authentication tokens without requiring traditional MFA prompts, enabling attackers to register devices and harvest emails within 78 seconds of victim authentication.
- The campaign distribution vector involves impersonating procurement officers from BJ's Wholesale Club via web contact forms, directing victims to WeTransfer links containing password-protected HTML files.
- The phishing kit employs a triple-layer obfuscation technique consisting of junk padding, character-level HTML comment injection, and AES-256-GCM encrypted redirect URLs to evade detection.
- Victims are forced to pass Cloudflare Turnstile challenges before being redirected to legitimate Microsoft sign-in pages, which they unwittingly use to authorize the attacker's device.
- Threat actors utilize residential proxy rotation to evade detection while harvesting data and registering three devices immediately after successful authentication.

## 3. Telemetry Mapping: OCSF Fields

### Summary
The GhostCode campaign utilizes a sophisticated device code phishing technique where victims are tricked into authorizing an attacker-controlled device via Microsoft's OAuth 2.0 Device Authorization Grant flow. The delivery mechanism involves password-protected HTML files with AES-256-GCM encryption and multi-layer obfuscation, distributed via WeTransfer links to impersonate procurement communications. Successful exploitation results in the rapid registration of devices and harvesting of Primary Refresh Tokens (PRT) by threat actors using residential proxy rotation to evade detection.

### Key Fields

OCSF path → the event field `knowledge/environment.md` documents for it.

- authentication:actor.user.name - Captures the identity of the victim user who unknowingly authorized the attacker's device during the OAuth consent screen phase.
- authentication:actor.device.hostname - Identifies the hostname or identifier of the 'device' being registered in the attack flow, which is controlled by the adversary rather than the legitimate user.
- file_activity.file.name - Detects the initial dropper file (e.g., password-protected HTML) delivered via WeTransfer that contains the obfuscated redirect URLs and encryption logic.
- file_activity.file.hashes.sha256 - Provides a static indicator to detect the specific encrypted HTML payload or subsequent tokens/scripts dropped by the GhostCode kit across different victims.
- network_activity.dst_endpoint.ip - Tracks connections from residential proxies used by the adversary to register devices and harvest PRTs, helping identify the rotation patterns distinct from standard user traffic.
- authentication:actor.session.id - Captures the session or token identifiers generated during the device code flow, which can be correlated with the short 78-second window of rapid token acquisition and email harvesting.

## 5. Research Synthesis

### Executive Summary
The GhostCode campaign exploits the Microsoft OAuth 2.0 device authorization grant flow via obfuscated HTML files distributed through WeTransfer, enabling adversaries to register attacker-controlled devices and harvest Primary Refresh Tokens within 78 seconds of user authentication. This technique bypasses traditional MFA controls by leveraging residential proxy rotation for token usage, effectively masking the origin of illicit identity access.

### Recommended Hypothesis
> Adversaries use OAuth 2.0 device code phishing via obfuscated HTML payloads to register unauthorized devices and harvest Primary Refresh Tokens on Microsoft 365 accounts.

### Gaps Identified
- Lack of telemetry correlating the specific Application ID (29d9ed98-a469-4536-ade2-f981bc1d605e) with rapid device registration events, combined with residential proxy rotation obscuring source IP reputation for token issuance.

### Key Findings
