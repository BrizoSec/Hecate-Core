## 1. System Research: How It Works

### Summary
The domain third-party.com, historically a documentation placeholder, has been compromised to serve ClickFix lures that mimic Cloudflare verification pages to Windows users. This attack poisons the clipboard with an obfuscated PowerShell command, tricking victims into manually executing remote code via the Windows Run dialog while serving harmless decoys to non-Windows operating systems.

### Key Findings
- The malicious page uses JavaScript to silently write a PowerShell one-liner to the clipboard and instructs users to execute it via Win+R, bypassing traditional file-based antivirus detection by using signed system binaries (PowerShell) for in-memory execution.
- The payload utilizes 'irm' (Invoke-RestMethod) to fetch a script from a second-stage server (elxxvvx[.]xyz) and 'iex' (Invoke-Expression) to execute it, suppressing errors with '2>$null' to avoid victim notice.
- The domain exhibits OS-specific content delivery, displaying a functional malware lure to Windows User-Agents while serving a benign 'macOS is not supported' error page to macOS/Linux agents, allowing it to evade detection by non-Windows security scanners and blocklists.
- The domain appears hardcoded in over 1,700 GitHub repositories from trusted sources (e.g., Chromium, Vercel), creating a supply chain risk where static documentation URLs point to attacker-controlled infrastructure rather than legitimate services.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries have compromised the widely used documentation placeholder domain third-party[.]com to serve ClickFix lures that target Windows users through a fake Cloudflare verification page. This technique abuses user trust in static code references and relies on social engineering to coerce victims into pasting malicious PowerShell commands from their clipboard into the Run dialog, thereby executing code without downloading suspicious files.

### Key Findings
- The domain third-party[.]com, historically used as a generic documentation placeholder similar to example.com, has been seized by attackers and is now serving OS-specific content: a malicious ClickFix lure for Windows users and a benign error message for macOS/Linux visitors.
- The attack employs the ClickFix method, where JavaScript silently poisons the user's clipboard with an obfuscated PowerShell one-liner (using Invoke-RestMethod to fetch and Invoke-Expression to execute code in memory) and instructs the victim to paste it into the Windows Run dialog via Win+R.
- The malicious domain is embedded in over 1,700 GitHub repositories from trusted sources including Chromium, Sanity, and Vercel, creating a widespread supply chain exposure where developers visiting documentation or testing environments may inadvertently trigger the lure.
- Detection is complicated by the fact that third-party[.]com serves clean decoys to non-Windows user agents and datacenter IP ranges, allowing it to evade automated security scanners and reputation feeds that do not simulate Windows desktop environments.
- The campaign leverages signed, trusted Windows binaries (PowerShell) rather than malicious executables, bypassing traditional antivirus scanning while relying on social engineering to compel the user to execute the payload themselves.

## 5. Research Synthesis

### Executive Summary
Adversaries have compromised the widely used documentation placeholder domain third-party[.]com to serve OS-specific ClickFix lures that silently poison the Windows clipboard with obfuscated PowerShell commands, coercing users into executing remote code via the Run dialog. This technique bypasses traditional file-based detection by leveraging signed system binaries (powershell.exe) for in-memory execution and evades scanner visibility through user-agent fingerprinting.

### Recommended Hypothesis
> Adversaries use OS-fingerprinted web delivery of clipboard-poisoned PowerShell one-liners to trick Windows users into manually executing remote code via the Run dialog, bypassing endpoint detection by avoiding file writes and utilizing trusted signed binaries.

### Gaps Identified
- Current telemetry lacks correlation between the specific obfuscated command line patterns (e.g., '&{iex(irm(...))}') pasted into interactive shell contexts (explorer.exe/runas.exe) and subsequent outbound network connections to secondary payload hosts, as standard process monitoring often ignores the 'pasting' action itself.
- Network detection is blind to initial request fingerprinting, as security scanners and reputation feeds typically query from non-Windows user agents or datacenter IPs, causing them to report benign decoy content while the actual malware payload remains undetected by automated threat intelligence feeds.

### Key Findings
- Hypothesis: Adversaries use OS-fingerprinted web delivery of clipboard-poisoned PowerShell one-liners to trick Windows users into manually executing remote code via the Run dialog, bypassing endpoint detection by avoiding file writes and utilizing trusted signed binaries.
- Gap: Current telemetry lacks correlation between the specific obfuscated command line patterns (e.g., '&{iex(irm(...))}') pasted into interactive shell contexts (explorer.exe/runas.exe) and subsequent outbound network connections to secondary payload hosts, as standard process monitoring often ignores the 'pasting' action itself.
- Gap: Network detection is blind to initial request fingerprinting, as security scanners and reputation feeds typically query from non-Windows user agents or datacenter IPs, causing them to report benign decoy content while the actual malware payload remains undetected by automated threat intelligence feeds.
- Focus: Hunt for anomalous process creation chains where 'powershell.exe' is spawned directly from 'explorer.exe' or 'runas.exe' via command lines containing obfuscated invocation methods (irm/iex) and suppressed error streams ($null), particularly when followed by immediate outbound DNS lookups to low-reputation or newly registered domains.
