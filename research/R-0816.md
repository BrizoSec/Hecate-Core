## 1. System Research: How It Works

### Summary
The STUN (Session Traversal Utilities for NAT) protocol normally facilitates network address translation discovery and UDP connectivity mapping between peers. In the context of Cling malware, this legitimate mechanism is abused to establish command-and-control channels, where malicious payloads are concealed within standard STUN transaction IDs to mimic legitimate Google infrastructure traffic.

### Key Findings
- The malware maintains persistence by replacing the system 'wget' binary (moving it to 'wget.r') and appending its own executables to multiple init scripts (/etc/inittab, /etc/init.d/rcS, /etc/rc.d/rc.boot) across SysV and BusyBox systems.
- Command-and-control communications are disguised as legitimate STUN Binding Requests sent every ~5 seconds to a list of 13 servers, including public infrastructure like stun.l.google.com (74.125.250.129), using IP spoofing to mask the origin.
- The botnet leverages vulnerabilities such as CVE-2021-35394 and CVE-2016-10372 to propagate across IoT devices, routers, and DVRs, while utilizing TCP tunneling and proxy relay capabilities for further exploitation.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
The Cling IoT botnet abuses the STUN protocol by masquerading command-and-control traffic as legitimate NAT-traversal queries to public servers, including those associated with Google, to evade detection. It propagates across vulnerable embedded devices via multiple CVE exploits and establishes persistence by replacing system binaries like wget and modifying init scripts.

### Key Findings
- Cling utilizes STUN protocol abuse for command-and-control, sending requests every ~5 seconds to a list of 13 servers (including 74.125.250.129 and stun.l.google.com) while spoofing source IPs to appear as Google infrastructure.
- The malware achieves persistence by copying itself to hidden paths (/root/.cling, /usr/local/bin/.cling), appending entries to init scripts (/etc/inittab, /etc/init.d/rcS), and hijacking the wget binary by moving it to wget.r and replacing it with the malware executable.
- Propagation is driven by exploitation of numerous vulnerabilities across routers and DVRs, specifically CVE-2021-35394, CVE-2014-8361, CVE-2023-26801, CVE-2024-3721, and others listed in the report.
- Botnet capabilities include DDoS flooding (targeting ports like 8080 for ISPs and 25565 for Minecraft), TCP tunneling, and proxy relay functions, with observed attack targets including South Korean ISPs and University of Chicago clusters.
- Indicators of Compromise include specific file hashes (e.g., SHA256: 90d738a8d650e3fefda9d7efa4baa11bd89ab05fcf0eb173e04aa01a52b465e2) identified as trojan.mirai/cling, and C2 IPs such as 145.249.115.184:3478 and 83.211.9.232:3478.

## 5. Research Synthesis

### Executive Summary
The Cling IoT botnet abuses the STUN protocol to mask Command-and-Control traffic as legitimate NAT-traversal queries, leveraging IP spoofing and public infrastructure like Google's STUN servers to evade detection. It achieves persistence by hijacking the wget binary and modifying SysV/BusyBox init scripts, while exploiting multiple CVEs to propagate across routers and DVRs.

### Recommended Hypothesis
> Adversaries use STUN protocol abuse and IP spoofing to conceal Command-and-Control communications within legitimate NAT-traversal traffic on IoT devices vulnerable to command injection flaws.

### Gaps Identified
- Standard network monitoring often fails to distinguish between legitimate STUN Binding Requests and malicious C2 payloads because the protocol structure itself is not inherently anomalous, and encryption may hide specific transaction ID contents.

### Key Findings
- Hypothesis: Adversaries use STUN protocol abuse and IP spoofing to conceal Command-and-Control communications within legitimate NAT-traversal traffic on IoT devices vulnerable to command injection flaws.
- Gap: Standard network monitoring often fails to distinguish between legitimate STUN Binding Requests and malicious C2 payloads because the protocol structure itself is not inherently anomalous, and encryption may hide specific transaction ID contents.
- Focus: Implement behavioral analysis of UDP flows to port 3478/19302 by correlating source IP reputation with STUN response patterns, and deploy file integrity monitoring on /etc/init.d/rcS, /etc/inittab, and the location of the wget binary to detect binary replacement or persistence script modifications.
