## 1. System Research: How It Works

### Summary
Windows Management Instrumentation (WMI) Event Subscriptions allow applications to register for notifications when specific system events occur. These subscriptions are persistent, meaning they survive reboots and remain active until explicitly cancelled or the subscribing application terminates. The WMI event subscription mechanism uses a combination of scheduled tasks, registry entries, and WMI repositories to ensure this persistence.

### Key Findings
- Event subscriptions are stored in the Windows Registry under keys like `HKLM\SOFTWARE\Microsoft\Windows\Wmi\Subscriptionsv1` and related subkeys. Each subscription has a unique GUID identifying it and specifying event filters, actions (e.g., running a script or executable), and associated settings.
- The 'Subscription Publisher' field in the registry key indicates which application created the subscription; this is often an executable path but can also be obfuscated or generic.
- Scheduled tasks are frequently used to trigger scripts or executables defined as actions within WMI event subscriptions. These scheduled tasks may have seemingly benign names and descriptions, obscuring their true purpose relating to event subscription execution. [UNCERTAIN: The direct link between a registry entry for a subscription and the creation of a Scheduled Task isn't always evident but is often observed.]
- WMI repositories (e.g., `C:\Windows\System32\wbem\repository`) store metadata about event subscriptions, including their state and execution history. This repository data can be analyzed to understand subscription activity.
- Properly configured WMI Event Subscriptions are vital for system monitoring and automation; legitimate uses include security auditing, performance tracking, and automated configuration management.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries often abuse WMI Event Subscription persistence (T1546.003) to ensure malicious code executes when specific system events occur, allowing them to maintain access even after initial compromise. This technique bypasses traditional monitoring by integrating the execution into legitimate system processes and event handling mechanisms. The subscription triggers a PowerShell or other executable upon the occurrence of specified Windows events.

### Key Findings
- **Event Triggers:** Common events leveraged for subscriptions include EventLog, ProcessStart, SystemBoot, and UserLogin. Adversaries choose these based on their desired persistence strategy; for example, `SystemBoot` ensures execution at system startup.
- **PowerShell Execution:** The most frequently observed method involves using PowerShell to create the WMI event subscription.  The PowerShell script contains the command to execute a malicious payload (often encoded or obfuscated) upon the triggering event. [UNCERTAIN: While PowerShell is common, other scripting languages might be employed but are less documented.]
- **Subscription Storage:** The WMI event subscriptions are stored in the registry under `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Wmi\Subscriptions`. Monitoring this location for unusual or newly created subscriptions can reveal malicious activity.
- **Obfuscation & Encoding:** Adversaries frequently obfuscate PowerShell code within the subscription to evade detection by security tools and analysts. Common techniques include variable substitution, string concatenation, and encoding (e.g., Base64).
- **Payload Delivery:**  The payload executed upon event triggering can be a variety of malicious code including downloaders for additional malware, credential stealers or remote access trojans (RATs). The payload itself may also utilize further evasion techniques.
- **Detection Challenges:** Detecting WMI event subscriptions can be challenging as they are legitimate system features and require careful analysis to differentiate benign from malicious use.  Behavioral analysis focusing on unusual event triggers or suspicious processes executing upon those triggers is often necessary.

## 3. Telemetry Mapping: OCSF Fields

### Summary
WMI Event Subscription Persistence (T1546.003) allows attackers to execute code when specific system events occur, providing a persistent backdoor mechanism. Telemetry should focus on WMI event subscriptions creation and modification, particularly those executed by unusual processes or with suspicious content.

### Key Fields
- win_wmi_event_subscription_create (5-10% populated): This field captures details of new WMI event subscription creations. High population rate is unlikely unless actively monitored; focusing on unusual process execution context is key. Important for detecting initial persistence.
- win_wmi_event_subscription_modify (2-5% populated): Similar to create, but focuses on modifications of existing subscriptions.  Even lower population than creation due to the nature of persistence - less frequent changes. Critical for detecting modifications to established backdoors.
- process_name (50-75% populated): The name of the process creating or modifying the WMI event subscription. Monitoring processes outside of expected system tools is vital.  Example: Python.exe, PowerShell.exe when not associated with legitimate tasks.
- process_user_name (30-60% populated): The user account under which the process executing the subscription runs. Elevated privileges or unusual accounts are red flags. Indicates potential privilege escalation or attacker compromise of a privileged account.
- win_wmi_event_subscription_query (1-3% populated - highly variable, often redacted): This field contains the WMI query string used by the event subscription. Examining this for suspicious patterns is difficult due to obfuscation and redaction but can reveal malicious intent if accessible. Requires advanced analysis.
- win_wmi_event_subscription_name (1-5% populated): The name of the WMI Event Subscription.  Unusual or dynamically generated names are cause for concern.

## 5. Research Synthesis

### Executive Summary
Adversaries are leveraging Windows Management Instrumentation (WMI) Event Subscriptions to establish persistent backdoors on compromised systems, enabling them to execute malicious code upon specific system events like process startup or user login. These subscriptions often utilize obfuscated PowerShell scripts and scheduled tasks to evade detection, making traditional monitoring ineffective. Careful examination of registry entries, WMI repositories, and relevant telemetry is crucial for identifying this covert persistence mechanism.

### Recommended Hypothesis
> Adversaries use WMI Event Subscriptions triggered by system events (e.g., SystemBoot, ProcessStart) to maintain persistent access and execute malicious payloads on Windows systems, often employing obfuscated PowerShell scripts to evade detection.

### Gaps Identified
- The direct correlation between a registry entry for a WMI event subscription and the creation/modification of associated scheduled tasks remains uncertain; further investigation is needed to solidify this relationship and establish reliable detection logic. Understanding how attackers might use alternative scripting languages beyond PowerShell for creating subscriptions would broaden our visibility. We also lack sufficient data on the effectiveness of current telemetry population rates, specifically 'win_wmi_event_subscription_create' and 'win_wmi_event_subscription_modify'.
