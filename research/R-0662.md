## 1. System Research: How It Works

### Summary
AWS automatically detects exposed IAM credentials in public repositories via GitHub's automated validity checks and neutralizes them by attaching the AWSCompromisedKeyQuarantine managed policy within approximately 10 seconds. This policy applies explicit Deny rules across 61+ permissions for 17 services to quarantine the key, allowing security teams to monitor these events through CloudTrail AttachUserPolicy logs.

### Key Findings
- AWS attaches the AWSCompromisedKeyQuarantineV3 managed policy to compromised IAM users within ~10 seconds of credential exposure, utilizing explicit Deny statements to block access across 61+ permissions spanning 17 services.
- Compromised keys are identified through GitHub's automated secret scanning process, which generates specific CloudTrail logs containing the user agent string 'GHAS-AWS_KEYID-validation-1.0.0' during GetCallerIdentity attempts.
- Security teams can detect quarantine events by monitoring CloudTrail for AttachUserPolicy log entries associated with the AWSCompromisedKeyQuarantine policy, as seen in test scenarios involving users like 'TestUser'.
- The automated validation process originates from GitHub's secret scanning infrastructure, identifiable by Go-based SDK user agents targeting the STS API on Linux/amd64 architectures.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries abuse exposed IAM credentials to perform unauthorized actions, such as creating roles or manipulating S3 objects, which are subsequently detected through GitHub Secret Scanning and CloudTrail monitoring. AWS automatically neutralizes these compromised keys by attaching managed policies like AWSCompromisedKeyQuarantine that enforce Deny rules, effectively locking down the account within seconds of detection.

### Key Findings
- AWS mitigates exposed IAM credentials by automatically attaching the AWSCompromisedKeyQuarantineV3 managed policy within 10 seconds of an access key's exposure, as evidenced by CloudTrail logs showing rapid policy attachment.
- The AWSCompromisedKeyQuarantine v1 managed policy specifically targets privilege escalation attempts by including Deny actions for iam:CreateRole and lambda:CreateFunction to prevent the creation of new roles or Lambda functions.
- The AWSCompromisedKeyQuarantineV2 managed policy includes s3:DeleteObject actions to restrict threat actors from deleting data, demonstrating a layered approach to neutralizing different abuse vectors.
- GitHub Secret Scanning (GHAS) validates potentially exposed AWS keys using automated processes identified by specific User-Agent strings containing 'GHAS-AWS_KEYID-validation-1.0.0', which updates periodically (e.g., in October 2025).
- Detection strategies rely on monitoring CloudTrail logs for the creation of IAM users (such as 'TestUser' in test scenarios) and the subsequent automatic attachment of quarantine policies to neutralize unauthorized usage.

## 5. Research Synthesis

### Executive Summary
AWS automatically neutralizes exposed IAM credentials by attaching the AWSCompromisedKeyQuarantineV3 managed policy within ~10 seconds of detection, blocking access across 61+ permissions via explicit Deny statements. Detection relies on identifying specific CloudTrail events for AttachUserPolicy alongside GitHub Secret Scanning user-agent strings in STS API logs.

### Recommended Hypothesis
> Adversaries use exposed IAM credentials to perform unauthorized actions on AWS services before being automatically locked out by automated policy attachment.

### Gaps Identified
- Lack of baseline correlation between high-volume STS GetCallerIdentity calls from non-standard Go SDK user agents and subsequent AttachUserPolicy events may allow initial exposure attempts to go unnoticed until the lockout occurs.
- Current monitoring likely misses the specific temporal window (<10 seconds) between credential validation and quarantine, failing to capture the transient state where the key was active before policy enforcement.
