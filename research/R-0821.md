## 1. System Research: How It Works

### Summary
This research describes an adversarial workflow where attackers validate stolen AWS credentials for Amazon Bedrock access using automated scripts that invoke specific APIs like GetCallerIdentity, ListFoundationModels, and Converse. These tools systematically test credentials across multiple regions to assess their value for resale in token-jacking markets, specifically targeting Anthropic Claude models and promotional credits.

### Key Findings
- Adversaries use a multi-step validation process starting with AWS STS GetCallerIdentity to confirm credential validity, followed by Amazon Bedrock-specific checks using ListFoundationModels and the Converse API (or InvokeModel) to verify LLM access capabilities.

- Analysis of malicious Python scripts on VirusTotal (hashes 92364136... and c9335bb8...) reveals systematic testing across multiple regions and additional enumeration of promotional credits via the billing: GetCredits API to assess financial value.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries utilize credential harvesting platforms like KMON_NOC to systematically validate stolen AWS keys, specifically testing for Amazon Bedrock access by enumerating foundation models and invoking Anthropic Claude APIs. This validation process determines the financial value of the credentials, particularly by checking for promotional credits, facilitating their resale in token-jacking markets at discounted rates.

### Key Findings
- Attackers validate AWS credentials using STS GetCallerIdentity before testing Bedrock access via ListFoundationModels and Converse API calls to distinguish general-purpose keys from those with LLM capabilities.
- Specific Python scripts identified on VirusTotal (Hashes: c9335bb8..., 92364136...) automate this process, targeting Anthropic Claude models and enumerating inference profiles via ListInferenceProfiles.
- The validation includes billing checks using the GetCredits API to assess the financial value of stolen accounts by identifying unused promotional credits for resale.
- The KMON_NOC platform actively extracts the AWS_BEARER_TOKEN_BEDROCK environment variable to facilitate the authentication and subsequent exploitation of Bedrock resources.
- Network indicators include IP addresses from diverse ISPs such as BIZNET NETWORKS (Indonesia), LG POWERCOMM (South Korea), and British Telecommunications, suggesting a distributed infrastructure for credential testing.

## 5. Research Synthesis

### Executive Summary
Adversaries utilize automated scripts to validate stolen AWS credentials for high-value Amazon Bedrock access by sequentially invoking STS GetCallerIdentity, ListFoundationModels, and Converse API endpoints to assess model availability and promotional credit balances. This behavior is characterized by specific file hashes (92364136..., c9335bb8...) executing against AWS API gateways from diverse IP ranges, facilitating the resale of AI compute resources in token-jacking markets.

### Recommended Hypothesis
> Adversaries use automated credential validation scripts invoking STS and Bedrock APIs to [assess financial utility of stolen accounts] on [AWS environments with LLM access capabilities]

### Gaps Identified
- Lack of visibility into unencrypted AWS SDK client-side logging or script content in memory, preventing detection of the specific Python payloads (e.g., aws.py) before they execute API calls over HTTPS.
- Insufficient correlation between STS GetCallerIdentity success logs and subsequent Bedrock ListFoundationModels/Converse invocations within short timeframes, allowing attackers to distinguish valid Bedrock-accessible keys from generic IAM roles without triggering volume-based alerts.

### Key Findings
- Hypothesis: Adversaries use automated credential validation scripts invoking STS and Bedrock APIs to [assess financial utility of stolen accounts] on [AWS environments with LLM access capabilities]
- Gap: Lack of visibility into unencrypted AWS SDK client-side logging or script content in memory, preventing detection of the specific Python payloads (e.g., aws.py) before they execute API calls over HTTPS.
- Gap: Insufficient correlation between STS GetCallerIdentity success logs and subsequent Bedrock ListFoundationModels/Converse invocations within short timeframes, allowing attackers to distinguish valid Bedrock-accessible keys from generic IAM roles without triggering volume-based alerts.
- Focus: Monitor for sequential API call patterns where GetCallerIdentity is immediately followed by Bedrock enumeration (ListFoundationModels) or inference attempts (Converse/InvokeModel) from the same source identity.
