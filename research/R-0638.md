## 1. System Research: How It Works

### Summary
SPIFFE/SPIRE provides workload identity through three components: a SPIFFE ID (canonical name), an SVID (cryptographic proof), and a Trust Bundle (verification authority). The system relies on the underlying Kubernetes node as a trusted boundary, using local selectors like cgroup metadata to issue short-lived credentials to co-located workloads.

### Key Findings
- The SPIRE agent communicates with workloads via a Unix domain socket at /run/spire/sockets/agent.sock, which is used by commands such as spire-agent api fetch jwt to retrieve identity tokens.
- Identity attestation relies heavily on cgroup path selectors; the specific cgroup hierarchy (e.g., kubepods-besteffort-pod...slice) determines the workload's identity rather than just its process UID or GID.
- A compromised node with root access can spoof workload identities by modifying cgroup metadata (e.g., writing to /sys/fs/cgroup/.../cgroup.procs), allowing an attacker to obtain valid SVIDs for other workloads on the same host without breaking cryptography.
- The SPIRE agent binary path was observed at /opt/spire/bin/spire-agent-1.12.4, and the Kubernetes service account token is stored at /var/run/secrets/kubernetes.io/serviceaccount/token, which may be leveraged in post-exploitation scenarios.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
Adversaries with root access on a compromised Kubernetes node can abuse SPIFFE/SPIRE by manipulating cgroup metadata to mislead the SPIRE agent into issuing valid SPIFFE Verifiable Identity Documents (SVIDs) for co-located workloads. This technique allows attackers to spoof workload identities and harvest SVIDs, enabling them to impersonate victim services within the cluster.


### Key Findings
- Attackers utilize root access on a compromised Kubernetes node to interact with the SPIRE agent via its Unix domain socket at /run/spire/sockets/agent.sock.
- The technique involves manipulating cgroup metadata; specifically, attackers create fake cgroup paths and append their own process IDs to cgroup.procs files to mimic legitimate workload locations.
- SPIFFE/SPIRE agents rely on cgroup information to identify workloads, allowing the attacker-controlled process to be misidentified as a co-located victim workload.
- Attackers use the spire-agent binary (e.g., /opt/spire/bin/spire-agent-1.12.4) with the 'api fetch jwt' command to request and harvest SVIDs for specific audiences, such as 'my-service'.
- The SPIRE agent's service account token, located at /var/run/secrets/kubernetes.io/serviceaccount/token, is utilized by the attacker to authenticate and facilitate these identity requests.
- Unit 42 has not observed this technique being exploited in the wild, and it remains a demonstrated post-exploitation capability rather than a confirmed active threat.

## 5. Research Synthesis

### Executive Summary
Adversaries with root access on compromised Kubernetes nodes can spoof workload identities by manipulating cgroup metadata to impersonate co-located services, bypassing cryptographic verification of the SPIFFE/SPIRE identity fabric. This technique relies on local node compromise rather than network interception, allowing attackers to harvest valid SVIDs via the local SPIRE agent socket for lateral movement and privilege escalation within the cluster.

### Recommended Hypothesis
> Adversaries use cgroup path manipulation and local SPIRE agent socket interaction to harvest valid SVIDs for co-located workloads on a compromised Kubernetes node

### Gaps Identified
- Lack of file integrity monitoring or syscall auditing on /sys/fs/cgroup/.../cgroup.procs allows undetected process injection into fake cgroup hierarchies
- Absence of telemetry correlating SPIRE agent binary execution (spire-agent) with local socket access (/run/spire/sockets/agent.sock) and subsequent JWT fetch events

### Key Findings
- Hypothesis: Adversaries use cgroup path manipulation and local SPIRE agent socket interaction to harvest valid SVIDs for co-located workloads on a compromised Kubernetes node
