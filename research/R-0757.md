## 1. System Research: How It Works

### Summary
Terraform is a configuration management tool that utilizes lock files to ensure provider version consistency; however, attackers weaponize these .terraform.lock.hcl files to redirect the 'terraform init' command to typosquatted registries controlled by the threat actor. This mechanism allows the adversary to masquerade as legitimate infrastructure code during job interviews, forcing the victim's environment to download and execute malicious binaries disguised as standard provider modules.

### Key Findings
- Weaponized GitHub repositories containing fake coding interview tasks utilize typosquatted domains (registry.hashicorp-aws[.]com, registry.hashicorp-aws[.]io, registry.hashicorp-terraform[.]io) in the .terraform.lock.hcl file to redirect Terraform provider downloads to attacker-controlled infrastructure.
- Execution of the malicious payload is triggered specifically by running 'terraform init' on the weaponized repository, which causes Terraform to treat the custom provider as the source of truth and execute the downloaded FLATROOF or ROOFDECK backdoors.
- The ROOFDECK backdoor implements anti-forensics and persistence techniques, including stripping quarantine attributes via 'xattr -rd com.apple.quarantine' and modifying file permissions with 'chmod +x' to bypass Gatekeeper checks on macOS.
- Implant activity is stealthily gated by the user's IDE usage; specifically, FLATROOF and ROOFDECK beaconing and execution were observed to occur primarily while the Cursor code editor was active, remaining dormant when the application was closed.

## 2. Adversary Tradecraft: Attack Techniques

### Summary
The DPRK-sponsored TraderTraitor group compromises DevOps engineers through fake job interview lures that deliver weaponized Terraform lock files, causing the execution of malicious custom providers from typosquatted domains. These initial footholds install macOS backdoors (FLATROOF and ROOFDECK) that enable credential theft and cloud environment escalation, as demonstrated in an attack on a non-cryptocurrency IT services provider following the LayerZero Labs breach.

### Key Findings
- Adversaries use fake job interview coding projects hosted on GitHub to deliver weaponized .terraform.lock.hcl files containing references to typosquatted provider domains (e.g., registry.hashicorp-aws.com) that mimic official HashiCorp registries.
- When a victim executes 'terraform init', the malicious lock file forces Terraform to download and execute custom provider modules from attacker-controlled servers, resulting in the installation of FLATROOF and ROOFDECK macOS backdoors.
- The campaign targeted a smaller IT services provider in India with no cryptocurrency ties, indicating an expanded scope beyond the initial high-profile LayerZero Labs attack which resulted in a $292 million theft.
- Backdoor activity is heavily stealthed by gating beaconing behavior to active Cursor IDE sessions, remaining dormant when the development tool is closed to avoid detection during off-hours.
- Post-compromise activities include reconnaissance, API key collection, and privilege escalation into AWS and Google Cloud Platform environments, with implants capable of self-rearming via gatekeeper bypass techniques (xattr/chmod) to maintain persistence.

## 5. Research Synthesis

### Executive Summary
TraderTraitor leverages typosquatted Terraform provider registries within weaponized .terraform.lock.hcl files to deliver FLATROOF and ROOFDECK macOS backdoors disguised as legitimate infrastructure modules. These implants exhibit sophisticated stealth by gating beaconing activity exclusively to active Cursor IDE sessions and bypassing Gatekeeper via xattr manipulation, necessitating detection strategies that correlate process lineage with network anomalies during development workflows.

### Recommended Hypothesis
> Adversaries use typosquatted Terraform lock files to deliver macOS backdoors that gate C2 beaconing to active IDE sessions to evade detection on DevOps workstations

### Gaps Identified
- Lack of telemetry correlating 'terraform init' network requests to non-HashiCorp domains allows initial provider download to go unnoticed without specific DNS or proxy logging
- Standard EDR alerts often miss 'nohup' executions spawned from IDE integrated terminals, failing to link the malicious binary launch to the parent Cursor process lineage

### Key Findings
- Hypothesis: Adversaries use typosquatted Terraform lock files to deliver macOS backdoors that gate C2 beaconing to active IDE sessions to evade detection on DevOps workstations
- Gap: Lack of telemetry correlating 'terraform init' network requests to non-HashiCorp domains allows initial provider download to go unnoticed without specific DNS or proxy logging
- Gap: Standard EDR alerts often miss 'nohup' executions spawned from IDE integrated terminals, failing to link the malicious binary launch to the parent Cursor process lineage
- Focus: Monitor for outbound network connections to typosquatted HashiCorp domains (registry.hashicorp-aws[.]com/io, registry.hashicorp-terraform[.]io) during 'terraform init' commands
- Focus: Detect simultaneous execution of Gatekeeper bypass techniques ('xattr -rd com.apple.quarantine') and privileged binaries disguised as system utilities (SystemUpdate/iSync) in user home directories
